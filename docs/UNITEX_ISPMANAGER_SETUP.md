# OFFICEPEAK: Unitex и запуск Nuxt в ISPmanager

Проект собирается как постоянное Node.js/Nitro-приложение. Каталог Unitex хранится отдельно от `.output` и перечитывается сервером при изменении файла, поэтому обновление каталога не требует новой сборки Nuxt.

## Как устроено обновление

1. CRON или администратор запускает `npm run catalog:sync:unitex`.
2. Скрипт авторизуется в Unitex API серверным токеном, получает разрешённые серии и список вариантов.
3. Подробные данные запрашиваются последовательными пакетами не более 25 записей, между запросами выдерживается не менее 5,5 секунды. HTTP 429 повторяется с увеличенной задержкой.
4. Ответ очищается от HTML, фильтруется белыми списками и преобразуется в `CatalogSnapshot`.
5. Новый снимок сначала записывается во временный файл и полностью проверяется. Предыдущий корректный снимок сохраняется как `unitexCatalog.last-good.json`, после чего рабочий файл заменяется атомарно.
6. Nitro замечает новое время изменения файла и перечитывает каталог. При ошибке остаётся кэшированная версия, затем `last-good`, а до первой синхронизации — демонстрационный каталог.

Unitex API никогда не вызывается из браузера или при открытии страницы. Токен и `unitexCatalog.meta.json` клиенту не выдаются. Метод `new_token` автоматически не вызывается.

## Подготовка Node.js-проекта в ISPmanager

Названия разделов могут немного отличаться в разных версиях ISPmanager.

1. Включите поддержку Node.js у домена/пользователя и выберите Node.js 22 LTS или более новую совместимую версию.
2. Создайте Node.js-приложение и укажите корнем каталог проекта, обозначенный ниже как `<APPLICATION_DIR>`.
3. В каталоге проекта выполните:

   ```bash
   npm ci
   npm run build
   ```

4. Укажите команду запуска:

   ```bash
   node .output/server/index.mjs
   ```

5. Порт задайте переменной `PORT`; Nitro читает её автоматически. Если панель задаёт порт сама, используйте выданное панелью значение.
6. После сборки перезапустите Node.js-приложение и проверьте `/api/catalog` и обычную страницу `/catalog`.

## Постоянная директория каталога

Создайте директорию, которую не удаляет повторное развёртывание приложения, например `<PERSISTENT_CATALOG_DIR>`. Она должна находиться вне `<APPLICATION_DIR>/.output` и быть доступна на чтение/запись тому же системному пользователю, от которого работают Node.js-приложение и CRON.

Скрипт управляет следующими файлами:

- `unitexCatalog.json` — рабочий снимок;
- `unitexCatalog.last-good.json` — предыдущий корректный снимок;
- `unitexCatalog.meta.json` — время синхронизации, версия API, срок токена, счётчики, предупреждения и SHA-256;
- `unitex-sync.lock` — временная блокировка параллельного запуска.

## Переменные окружения

Добавьте их в окружение Node.js-приложения и в окружение CRON. Не добавляйте реальные значения в Git.

```dotenv
PORT=<PORT_FROM_ISPMANAGER>
UNITEX_API_TOKEN=<UNITEX_API_TOKEN>
UNITEX_CATALOG_STORAGE_DIR=<PERSISTENT_CATALOG_DIR>
UNITEX_SYNC_CITY=moscow
UNITEX_API_BASE_URL=https://api.unitex.ru/
UNITEX_SYNC_TIMEOUT_MS=21600000
UNITEX_SYNC_MAX_RETRIES=4
```

`UNITEX_API_TOKEN` — серверный секрет. Не называйте его `NUXT_PUBLIC_*`. SMTP-переменные настраиваются отдельно по инструкции `docs/SMTP_SETUP.md`.

При локальном запуске `npm run catalog:sync:unitex` автоматически загружает переменные из рабочего файла `.env`, если он существует. Файл `.env.example` служит только образцом и никогда не используется как источник секретов. В ISPmanager те же переменные можно задавать в окружении приложения и CRON без создания `.env`.

## Белый список

Настройки находятся в `config/unitex-sync.json`.

- `allowedSeriesCodes` — разрешённые коды серий; список не может быть пустым.
- `allowedSetCodes` — разрешённые коды специальных подборок Unitex из метода `sets`; товары подборки получают её как основную коллекцию и не дублируются в серии.
- `productionOurOnly` — при значении `true` в каталог проходят только записи с официальным признаком Unitex `production_our = 1`. Записи с `0` или без этого признака не запрашиваются и не публикуются.
- `allowedBaseProductIds` — разрешённые `base_id`. Пустой массив означает все базовые товары, но только внутри разрешённых серий.
- `allowedVariantIds` — разрешённые ID записей товара/вариантов. Пустой массив означает все варианты выбранных базовых товаров.
- `currency` — валюта API, по умолчанию `RUR`.
- `priceType` — только публичная розничная цена `retail`; оптовые значения не публикуются.
- `maxSeriesImages` — максимальное число изображений серии.
- `categoryByUnitexId` — сопоставление ID категории Unitex со slug/ID категории сайта.

Вся серия `urus`:

```json
{
  "allowedSeriesCodes": ["urus"],
  "allowedBaseProductIds": [],
  "allowedVariantIds": []
}
```

Несколько базовых товаров:

```json
{
  "allowedSeriesCodes": ["urus"],
  "allowedBaseProductIds": ["<BASE_ID_1>", "<BASE_ID_2>"],
  "allowedVariantIds": []
}
```

Отдельные варианты:

```json
{
  "allowedSeriesCodes": ["urus"],
  "allowedBaseProductIds": [],
  "allowedVariantIds": ["<VARIANT_ID_1>", "<VARIANT_ID_2>"]
}
```

Сохраняйте остальные поля исходного конфигурационного файла при изменении белого списка.

## Первая синхронизация

Сначала выполните проверку без публикации снимка:

```bash
cd <APPLICATION_DIR>
npm run catalog:sync:unitex -- --dry-run
```

Затем запустите запись:

```bash
npm run catalog:sync:unitex
```

Проверьте журнал команды, файлы в `<PERSISTENT_CATALOG_DIR>`, ответ `/api/catalog` (`source` должен стать `unitex`) и несколько страниц товаров. Перезапуск приложения не требуется.

## CRON в ISPmanager

Рекомендуемый интервал — один раз в час. Узнайте пути к Node.js и npm в терминале того же Node.js-окружения (`which node`, `which npm`) и подставьте реальные значения:

```cron
7 * * * * cd <APPLICATION_DIR> && <PATH_TO_NPM> run catalog:sync:unitex >> <LOG_DIR>/unitex-sync.log 2>&1
```

Не используйте выдуманные пути из примера. В задании должен работать тот же пользователь и та же версия Node.js, что и у приложения. Сам синхронизатор дополнительно блокирует параллельные запуски через `unitex-sync.lock`.

Для проверки журнала:

```bash
tail -n 100 <LOG_DIR>/unitex-sync.log
```

## Обновление токена

Если в метаданных или журнале появилось предупреждение о сроке менее суток:

1. Получите новый токен вручную утверждённым способом Unitex. Автоматический вызов `new_token` намеренно отключён.
2. Замените значение `UNITEX_API_TOKEN` в окружении Node.js и CRON.
3. Выполните `npm run catalog:sync:unitex -- --dry-run`.
4. При успехе выполните обычную синхронизацию.

Не вставляйте токен в командную строку, конфигурацию, документацию или клиентский код.

## Восстановление last-good

Если рабочий JSON повреждён, работающий процесс продолжит использовать последнюю версию из памяти. После перезапуска сервер попробует `unitexCatalog.last-good.json`, затем демонстрационный каталог.

Для явного восстановления остановите синхронизацию, убедитесь, что резервный файл корректен, и выполните атомарную замену в постоянной директории:

```bash
cd <PERSISTENT_CATALOG_DIR>
cp -- unitexCatalog.last-good.json unitexCatalog.restore.tmp
mv -f -- unitexCatalog.restore.tmp unitexCatalog.json
```

После этого откройте `/api/catalog` и страницу товара. Для возврата к демонстрационному каталогу временно переместите оба Unitex-снимка из постоянной директории в отдельную резервную папку и перезапустите приложение.
